Chapter 3 Seurat workflow

3.1 What we are doing in this chapter

In the previous chapter, we removed empty droplets and obtained filtered count matrices for our four samples. Now we need to go from raw counts to clusters and cell types. This is really the core of any single-cell analysis.

Here’s the overall pipeline:

Raw counts → Seurat object → QC filtering → Normalization → Variable genes →
Scaling → PCA → Integration → UMAP → Clustering → Marker genes → Interpretation

That looks like a lot of steps, but the nice thing is that they all follow a standard pattern. Let me briefly walk you through each one:

  1. Create Seurat Object – organize counts into an S4 object that holds your data, metadata, and analyses in one place.
  2. Additional QC Filtering – filter cells by gene counts, mitochondrial %, ribosomal %. Empty droplet removal (Chapter 2) was just the first pass.
  3. Normalization – divide by library size, multiply by 10,000, log transform. Cells have different sequencing depths and we need to make them comparable.
  4. Find Variable Features – pick the ~2,000 most variable genes. Housekeeping genes don’t help you cluster.
  5. Scale Data – Z-score each gene so that highly expressed genes don’t dominate PCA.
  6. Run PCA – go from 2,000 genes down to ~30 principal components. This filters out noise.
  7. Integrate with Harmony – remove sample-specific batch effects while keeping real biology.
  8. Run UMAP – project 30 PCs down to 2 dimensions so you can actually see what’s going on.
  9. Find Neighbors + Clusters – build a k-nearest-neighbor graph, apply Louvain clustering. Cells with similar expression profiles end up in the same cluster.
  10. Find Marker Genes – differential expression testing to figure out what each cluster actually is.

What we’re doing here is exploratory analysis: start with raw data, cluster unsupervised, discover cell populations. We’re asking “what cell types are present?” This is hypothesis-generating, not hypothesis-testing. If you want to do something like “do activated vs resting T cells differentially express cytokines?” – that’s a confirmatory analysis and requires a different statistical framework (pseudo-bulk DE, which we’ll touch on later).

3.1.1 How I structured this chapter

I decided to first run the entire pipeline so you can see the results, and then go back and unpack the math behind each step. In my experience, it’s much easier to understand why normalization works a certain way after you’ve already seen it in action. So don’t skip the math sections later – we’ll manually verify LogNormalize, dig into how log2 fold changes are calculated (Seurat and Scanpy do it differently!), and talk about how to choose parameters.

By the end, you’ll know:

  • How many distinct cell populations are in our PBMC samples
  • What marker genes define each population
  • Whether there are batch effects between samples/donors
  • Whether activated vs resting T cells separate into different clusters
  • How to spot and remove low-quality clusters

3.3.1 cellranger input

If you used cellranger instead of simpleaf for quantification, the output directory structure looks like this:

sample/outs/filtered_feature_bc_matrix/
├── barcodes.tsv.gz    # one barcode (cell) per line
├── features.tsv.gz    # gene IDs and gene names
└── matrix.mtx.gz      # the sparse count matrix in Matrix Market format

These three files together define the count matrix. matrix.mtx.gz stores only the non-zero entries (row index, column index, count value), and the other two files tell you which row corresponds to which gene and which column corresponds to which cell.

You point Read10X() to the directory containing these three files:

# pass the path to the directory, not to individual files
counts <- Seurat::Read10X(data.dir = "sample/outs/filtered_feature_bc_matrix/")

# this returns a sparse matrix, which you can pass to CreateSeuratObject()
obj <- CreateSeuratObject(counts = counts, project = "my_sample")

If you have multiple samples from cellranger, you can read them in one by one and then merge:

# read in each sample
sample1 <- Read10X(data.dir = "sample1/outs/filtered_feature_bc_matrix/")
sample2 <- Read10X(data.dir = "sample2/outs/filtered_feature_bc_matrix/")

obj1 <- CreateSeuratObject(counts = sample1, project = "sample1")
obj2 <- CreateSeuratObject(counts = sample2, project = "sample2")

# merge into one object
obj <- merge(obj1, y = obj2, add.cell.ids = c("sample1", "sample2"))

The add.cell.ids argument prepends the sample name to each cell barcode so you can tell which sample each cell came from after merging. If you have many samples, you can use a loop or purrr::map() as we showed in Chapter 2.

One thing to watch out for: cellranger provides both a filtered_feature_bc_matrix (cells that passed cellranger’s built-in cell calling) and a raw_feature_bc_matrix (all barcodes including empty droplets). If you want to do your own cell calling with emptyDrops(), use the raw matrix. If you trust cellranger’s filtering, use the filtered one.

3.6 Routine Processing

Now we’re ready to run the standard Seurat workflow.

3.6.1 Why do we need dimensionality reduction?

Our data has ~20,000 dimensions (one per gene). You can’t cluster or visualize that directly. In high-dimensional space, distances become meaningless, noise dominates signal, and computation is slow. We need to reduce dimensions while keeping the interesting structure.

We do this in two stages:

First, PCA takes us from 20,000 genes down to ~30 principal components. PCA finds directions of maximum variance – you can think of PCs as linear combinations of genes that capture co-expression patterns. Most of the biological signal lives in the first 20-30 PCs; the rest is mostly noise.

Then, UMAP takes those 30 PCs down to 2 dimensions for visualization. UMAP preserves local neighborhood structure, so cells that are similar in 30-dimensional PC space stay close together in the 2D plot. It’s faster than t-SNE and generally preserves global structure better.

3.6.2 Why we need integration (Harmony)

Our four samples have technical variation – different library prep, different sequencing runs, different donors. Without batch correction, cells can cluster by sample rather than by cell type, which is not what we want.

Harmony works on the PC embeddings. Conceptually, it identifies cells that should be similar across batches, learns correction factors, and adjusts the embeddings to remove batch effects while preserving real biology (cell types, activation states).

When should you integrate? When you have multiple samples with expected technical variation and you care about biological differences, not batch differences. If your samples mix well on the UMAP without integration, you might not need it at all.

There are alternatives – FastMNN (mutual nearest neighbors, the OSCA default), scVI (deep learning-based, more powerful but more complex), and Seurat’s own CCA/RPCA methods. We use Harmony here because it’s fast, simple, and works well for typical batch correction.

3.6.2.1 But should you always integrate?

This is one of the most common questions I get. You’ve got PBMCs from multiple donors – do you integrate or not? The answer depends on your biological question.

If you integrate, cells cluster by cell type rather than by donor. Donor-specific and batch-specific differences get smoothed out, and you get a unified UMAP where the same cell types from different samples sit together. This is great when you want to count cell types across donors, annotate clusters consistently, or build a reference atlas.

If you don’t integrate, cells tend to cluster by donor, even within the same cell type. You retain sample-specific variation, but alignment across samples is harder.

Here’s my rule of thumb:

  • Want to count B cells across donors? Integrate.
  • Want to find activated B cells that only appear in COVID patients? Don’t integrate – you might smooth away exactly the signal you’re looking for.

In practice, I often do both: integrate first to get consistent cluster labels, then go back to the uncorrected data to ask condition-specific questions.

One important thing to understand about Harmony: it corrects only the PCA embeddings. It does not change the original count matrix or the normalized expression values. So after you get consistent cluster labels from the integrated analysis, you use the raw counts for differential expression across conditions within the same cell type. The integration affects clustering and UMAP, not the DE results.

For more on when to integrate and when not to, read:

  • The OSCA book chapter on integration: https://bioconductor.org/books/3.20/OSCA.multisample/integrating-datasets.html#no-correction
  • Valentine Svensson’s post on this topic: https://substack.com/@valentinesvensson/p-159305684

3.6.3 The pipeline in one code block

Let’s run everything at once, then we’ll unpack each step later:

#install.packages("harmony")
library(harmony) 

obj<- obj %>%
  NormalizeData(normalization.method = "LogNormalize", scale.factor = 10000) %>%
  FindVariableFeatures(selection.method = "vst", nfeatures = 2000) %>%
  ScaleData() %>%
  RunPCA() %>%
  RunHarmony(group.by.vars = "sample", dims.use = 1:30) %>%
  RunUMAP(reduction = "harmony", dims = 1:30) %>%

3.6.4 How to choose parameters

There’s no single “correct” set of parameters, but there are principled ways to choose them. Let me walk through each choice we made:

3.6.4.1 Normalization

NormalizeData(normalization.method = "LogNormalize", scale.factor = 10000)

We’re using LogNormalize here – it’s fast, interpretable, and good for exploratory analysis. The scale factor of 10,000 is just convention (makes normalized counts a similar scale to raw counts). Some people use 1e6 (CPM), but it doesn’t matter much for downstream clustering.

The main alternative is SCTransform, which does a better job of variance stabilization. Consider SCTransform if you have very heterogeneous datasets (lots of different cell types) or if you care about precise gene expression levels, not just clustering. It’s more computationally intensive but often gives better results.

3.6.4.2 Variable features

FindVariableFeatures(selection.method = "vst", nfeatures = 2000)

We use vst (variance stabilizing transformation), which is the default and works well. 2,000 features is the standard – it’s a good balance of signal vs noise. You can go as low as 500-1,000 (faster, but might miss subtle populations) or up to 5,000+ (but at that point you’re probably adding more noise than signal).

You can check your choice by plotting the variable features:

# Identify the 10 most highly variable genes
top10 <- head(VariableFeatures(obj), 10)

# Plot variable features with labels
VariableFeaturePlot(obj)
LabelPoints(plot = VariableFeaturePlot(obj), points = top10, repel = TRUE)

3.6.4.3 PCA dimensions

RunPCA()  # Computes 50 PCs by default
# ...later: dims = 1:30

We use the first 30 PCs for downstream analysis. How do you decide? The elbow plot shows where adding more PCs stops explaining much variance:

ElbowPlot(obj, ndims = 50)

A sharp drop-off suggests a clear signal vs noise boundary. A gradual decline means biological signal extends to many PCs.

As a rough guide: 10-15 PCs for small datasets with clear cell types (e.g., pure T cells), 20-30 for most datasets, and 40-50 for complex datasets with many cell types (e.g., whole organism atlas). We use 30 here – conservative, captures most biological variation without including noise PCs.

For heterogeneous datasets, err on the side of using more PCs (30-50). For homogeneous datasets, fewer PCs (15-30) are usually fine. The elbow plot is your guide. See sc-best-practices.org for more discussion.

3.6.4.4 Clustering resolution

FindClusters(resolution = 0.4)

Resolution = 0.4 gives us a moderate number of clusters. Lower resolution (0.1-0.4) gives fewer, broader clusters; higher resolution (0.8-2.0) gives many fine-grained clusters.

The right resolution depends on your question. Want major cell types? Use 0.2-0.5. Want cell subtypes and states? Try 0.8-1.5. In my experience, the best approach is to try multiple resolutions and compare:

# Try multiple resolutions

# Visualize with clustree
library(clustree)
clustree(obj, prefix = "RNA_snn_res.")

clustree shows how clusters split as resolution increases – it helps you see which clusters are stable and which ones are artifacts of over-splitting.

We went with 0.4 here, which gives ~10 clusters. That’s reasonable granularity for PBMC T cells – we expect CD4 T, CD8 T, possibly NK, and activation states.

3.6.4.5 Integration

RunHarmony(group.by.vars = "sample", dims.use = 1:30)

We’re correcting for the sample effect using the first 30 PCs. But do you actually need integration? Check first:

# Before integration: compute UMAP on uncorrected PCs
obj_uncorrected <- RunUMAP(obj, reduction = "pca", dims = 1:30)
DimPlot(obj_uncorrected, group.by = "sample")

# After integration: compute UMAP on Harmony-corrected PCs
DimPlot(obj, group.by = "sample")

If samples already mix well before integration, you might not need it at all. Don’t integrate just because everyone else does.

If you do need it, you can also try FastMNN for stronger batch effects, or use group.by.vars = c("sample", "donor") to correct for multiple batch variables at once.

3.8 Understanding the math behind each step

OK, so the pipeline above is only a couple lines of code, but there’s a lot happening under the hood. Let’s go through the important parts.

3.8.1 Why do we normalize?

Different cells have different total UMI counts (library sizes). Some of this is technical (sequencing depth), some is biological (some cells are just more transcriptionally active). Here’s the problem: a gene with 100 counts in cell A (10,000 total UMIs) vs 50 counts in cell B (5,000 total UMIs) looks differentially expressed – but it’s actually expressed at the same proportion. We normalize by library size to make cells comparable.

3.8.2 LogNormalize: what exactly does it do?

NormalizeData() does three things: divide by library size (total UMIs per cell), multiply by a scale factor (default 10,000), and natural log transform (with a pseudocount of +1).

The formula:

\[ \text{norm}_{ij} = \log\left(\frac{X_{ij}}{\sum_{j} X_{ij}} \times 10000 + 1\right) \]

Where \(X_{ij}\) is the raw count for gene \(i\) in cell \(j\), and \(\sum_{j} X_{ij}\) is the total UMI count for cell \(j\) (the library size).

Why log transform? Three reasons: it stabilizes variance (raw counts have heavy tails), it turns fold changes into differences (easier for linear models), and it scales genes to similar ranges so highly expressed genes don’t dominate PCA.

3.8.3 When to use different normalization methods

LogNormalize is the default, but it’s not always the best choice. Let me walk through the options.

LogNormalize (what we used) is fast, memory-efficient, and interpretable. It works well for homogeneous datasets (e.g., all T cells, all neurons) and exploratory clustering. The downside: it doesn’t model the mean-variance relationship and can be dominated by highly expressed genes.

SCTransform:

obj <- SCTransform(obj, vars.to.regress = "percent.mt")

SCTransform uses a regularized negative binomial model for better variance stabilization. It accounts for the mean-variance relationship and can regress out technical covariates (MT%, cell cycle). It often improves clustering and DE testing. The tradeoff is that it’s slower, more memory-intensive, and can over-correct if you’re not careful.

Use SCTransform for heterogeneous datasets with many cell types, when you need precise variance estimates, or when you want to regress out confounders. It’s now recommended over LogNormalize for most analyses (see Choudhary & Satija 2022), and recent Seurat versions have made it faster.

scran normalization:

library(scran)
# Deconvolution-based normalization (OSCA approach)
sce <- computeSumFactors(sce, clusters = quickCluster(sce))
sce <- logNormCounts(sce)

scran uses deconvolution-based normalization that accounts for composition biases (different cell types have different total RNA content). It’s the approach recommended by the OSCA book and works well for multi-sample experiments. The downside is you need to switch to the SingleCellExperiment framework.

Use scran when you have strong composition biases (e.g., comparing embryonic stages) or when you want the theoretical guarantees that come with the OSCA approach.

3.8.4 Which normalization should you use?

For this tutorial, we use LogNormalize because it’s fast, interpretable, and our dataset is relatively homogeneous (all PBMCs, mostly T cells). For your own analysis, I’d suggest starting with LogNormalize to explore quickly. If clustering looks noisy or dominated by technical variation, try SCTransform. For publication-quality analysis, it’s worth comparing results with multiple normalization methods.

One nice trick – you can store multiple normalized versions in the same Seurat object:

# Keep LogNormalize in the RNA assay
obj <- NormalizeData(obj)

# Add SCTransform as a separate assay
obj <- SCTransform(obj, assay = "RNA", new.assay.name = "SCT")

# Switch between them
DefaultAssay(obj) <- "RNA"   # Use LogNormalize
DefaultAssay(obj) <- "SCT"   # Use SCTransform

This lets you compare results without re-running the entire pipeline.

3.8.7.3 Pseudo-bulk + DESeq2/edgeR (for multi-sample comparisons)

Here’s something important that a lot of people get wrong: each cell is not an independent observation. Cells from the same sample are correlated, so treating them as independent inflates false positives. For multi-sample/multi-condition comparisons, you should aggregate counts to pseudo-bulk per sample, then use DESeq2 or edgeR. See the sc-best-practices.org differential expression chapter for more details.

Use pseudo-bulk when you have biological replicates, when you want to compare conditions (activated vs resting T cells), or when you need proper statistical inference. For exploratory marker gene discovery within one sample, Wilcoxon is fine.

We’re doing exploratory marker discovery here, so Wilcoxon is appropriate. For comparing activated vs resting conditions properly, you’d want the pseudo-bulk approach. (we will go over it in the later of this chapter).

Note that the p-values are very small. When you have hundreds or thousands of cells per cluster, the p-values will be very small. The p-value in statistical tests, including the Wilcoxon rank-sum test (also known as the Mann-Whitney U test), is influenced by both the sample size and the effect size (the magnitude of the difference between the groups being compared).

Generally, as the sample size increases, the p-value tends to decrease, assuming there is a non-zero effect size.

3.8.7.5 How log2 Fold change is calculated?

There is nuances in how the log2 Fold change is calculated. Scanpy and Seurathave different implementations. See this twitter thread https://twitter.com/lpachter/status/1694387749967847874

Old Seurat formula:

\(R_{g}=\log_{2}(\frac{1}{n_{1}}\sum_{i\in G_{1}}(exp(Y_{ig})-1)+1)-log_{2}(\frac{1}{n_{2}}\sum_{i\in G_{2}}(exp(Y_{ig})-1)+1),\)

New Seurat formula (instead of plus 1, it uses a small value \(\epsilon\):

\(R_{g}=\log_{2}(\frac{1}{n_{1}}\sum_{i\in G_{1}}(exp(Y_{ig})-1)+\epsilon)-log_{2}(\frac{1}{n_{2}}\sum_{i\in G_{2}}(exp(Y_{ig})-1)+\epsilon),\)

Scanpy formula:

\(P_{g}=\log_{2}(exp(\frac{1}{n_{1}}\sum_{i\in G_{1}}Y_{ig})-1+\epsilon)-log_{2}(exp(\frac{1}{n_{2}}\sum_{i\in G_{2}}Y_{ig})-1+\epsilon),\)

where \(\epsilon=10^{-9}\).

where \(Y_{ig}\) are the log-transformed expression values for cell \(i\) and gene \(g\), \(G_{1}\) and \(G_{2}\) are the indices for two groups of cells, and \(n_{1}\) and \(n_{2}\) are the numbers of cells in the respective groups.

3.9 Doublet detection

In droplet-based scRNA-seq, sometimes two cells get captured in the same droplet. The resulting “cell” has a mixed transcriptome from both, and it can really mess up your analysis – doublets often end up between clusters on a UMAP, or they form their own weird cluster that looks like a hybrid cell type that doesn’t actually exist.

The expected doublet rate depends on how many cells you load. For 10x Genomics, it’s roughly 0.8% per 1,000 cells captured. So if you captured 10,000 cells, expect around 8% doublets. That’s not trivial.

There are several computational doublet detection tools. A benchmarking paper by Xi and Li (2021) compared many of them. I like scDblFinder – it’s fast, accurate, and works well in practice. See also the OSCA chapter on doublet detection for a thorough discussion of the different approaches.

The basic idea: scDblFinder simulates artificial doublets by combining random pairs of cells, then trains a classifier to distinguish real cells from these artificial doublets. Cells that look similar to the artificial doublets get flagged.

# BiocManager::install("scDblFinder")

3.10 Ambient RNA removal

Here’s a problem most beginners don’t think about: when cells are lysed during the droplet capture process, their mRNA spills into the surrounding solution. This “ambient RNA” or “soup” gets captured in every droplet, so every cell’s expression profile is contaminated with background signal from the most highly expressed genes in the lysed cells.

In practice, this means you’ll see low-level expression of hemoglobin genes in your T cells, or mitochondrial genes everywhere. It’s not real expression – it’s contamination. If you don’t correct for it, you might call a cluster “T cells with some erythroid features” when really it’s just T cells swimming in hemoglobin soup.

Two popular tools for this: SoupX and decontX. SoupX needs the unfiltered (raw) count matrix in addition to the filtered one, because it estimates the ambient profile from the empty droplets. decontX doesn’t need the raw matrix, which makes it easier to use when you only have the filtered counts. I’ll use decontX here.

For more background, see 10x Genomics’ guide on ambient RNA and the decontX vignette.

decontX uses a Bayesian model to estimate the contamination fraction in each cell and produces corrected counts. We first need to subset the SCE object to match our doublet-filtered Seurat object:

3.12 Pseudo-bulk differential expression with DESeq2

Earlier, I mentioned that FindAllMarkers treats each cell as an independent observation. That’s fine for exploratory marker discovery (“what genes define this cluster?”), but it’s wrong for testing differences between conditions (“do activated T cells express more cytokines than resting T cells?”).

Why? Because cells from the same sample are not independent. If you have 2,000 CD4 T cells from donor A and 1,500 from donor B, you don’t have 3,500 independent observations – you have 2 biological replicates. Treating cells as independent massively inflates your false positive rate. This is one of the most common mistakes I see in single-cell papers. See Squair et al. (2021), “Confronting false discoveries in single-cell differential expression.”

The solution: aggregate counts from all cells of the same type within a sample into a “pseudo-bulk” profile, then use standard bulk RNA-seq tools like DESeq2 or edgeR. This is called pseudo-bulk analysis, and it’s the recommended approach for multi-sample, multi-condition comparisons.

I wrote a blog post about this: https://divingintogeneticsandgenomics.com/post/how-to-create-pseudobulk-from-single-cell-rnaseq-data/

Let’s walk through the full workflow with our PBMC data.

3.12.1 Step 1: Aggregate counts to pseudo-bulk

The idea is simple: for each cell type (cluster) in each sample, add up the raw counts across all cells. If you have 500 CD4 T cells from sample SRX5329394, you sum their counts gene-by-gene into one column. This gives you one “pseudo-bulk” profile per cluster per sample.

3.12.4 Step 4: Run DESeq2 for all clusters with purrr

You see the pattern – we wrote code for one cluster, now we can iterate over all clusters. Same principle as Chapter 2.

run_deseq2_cluster <- function(cluster_id, pseudo_bulk, pseudo_meta) {
  # Subset to this cluster
  cluster_cols <- pseudo_meta %>%
    dplyr::filter(cluster == cluster_id) %>%
    pull(id)

  counts_sub <- pseudo_bulk[, cluster_cols]
  meta_sub <- pseudo_meta[cluster_cols, ]

  # Need at least 2 samples per condition
  if (any(table(meta_sub$condition) < 2)) {
    return(NULL)
  }

  # Create DESeq2 object
  dds <- DESeqDataSetFromMatrix(countData = counts_sub,
                                 colData = meta_sub,
                                 design = ~ condition)

  # Filter low-count genes
  keep <- rowSums(counts(dds)) >= 10
  dds <- dds[keep, ]

  # Run DESeq2
  dds <- DESeq(dds)

  # Get results
  res <- results(dds, contrast = c("condition", "activated", "resting"))
  res_df <- as.data.frame(res) %>%
    tibble::rownames_to_column("gene") %>%
    arrange(padj) %>%
    mutate(cluster = cluster_id)

  return(res_df)
}

3.12.6 When to use pseudo-bulk vs FindAllMarkers

To be clear about when to use each:

  • FindAllMarkers: “What genes define this cluster?” – comparing one cluster vs all others. Good for marker discovery. Each cell is a data point, and that’s OK here because you’re characterizing clusters, not testing conditions.

  • Pseudo-bulk DESeq2: “What genes change between conditions within this cell type?” – comparing activated vs resting within CD4 T cells, for example. You must aggregate to pseudo-bulk because cells within a sample are not independent.

I see people use FindMarkers(obj, ident.1 = "activated", ident.2 = "resting") to compare conditions. This is wrong if you have multiple samples. You’ll get tons of “significant” genes, but most are false positives. Use pseudo-bulk.

3.13.1 Things that go wrong

I’ve seen all of these in practice:

  • Blindly using default parameters. Always check elbow plots, try multiple resolutions, visualize before and after integration. Don’t just copy-paste the pipeline and call it a day.
  • Over-integrating. Too aggressive integration removes real biological signal. After integrating, check that your condition effects (activated vs resting) are still there.
  • Treating Wilcoxon p-values as definitive. These assume cell independence, which is violated in scRNA-seq. Use them for ranking markers, not for hypothesis testing.
  • Not plotting QC metrics on your clusters. Always plot percent.mt, nFeature_RNA on your final UMAP. I’ve caught artifact clusters this way more than once.
  • Ignoring doublets and ambient RNA. These confound everything downstream. Check doublet scores and contamination levels.
  • Sticking with one normalization method. When in doubt, try SCTransform and compare. Sometimes it reveals populations that LogNormalize misses.
